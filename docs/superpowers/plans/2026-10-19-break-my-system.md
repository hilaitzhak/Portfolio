# Break My System Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a "Break my system" page to the portfolio. An animated online-orders system runs in the browser, visitors press chaos buttons and watch it recover, and Claude writes an incident report from the session's real event log.

**Architecture:** A deterministic TypeScript simulation engine (queue with acks and redelivery, workers, idempotency, backoff, dead-letter queue, autoscaling) runs in the browser and is unit tested. A React page renders it. One AWS Lambda (Node.js, Function URL) validates a structured event log, enforces rate limits and a daily cap in DynamoDB, and calls the Claude API. The page lives at `#break-my-system`, using the same hash-view pattern as `CaseStudy.tsx`.

**Tech Stack:** React 18 + TypeScript (Create React App, Jest via `react-scripts test`), Node.js 20 Lambda with `@anthropic-ai/sdk` and `@aws-sdk/client-dynamodb`, `node:test` for Lambda tests, AWS CLI with the `personal` profile.

**Spec:** No separate spec file. The design was agreed in conversation and is summarised under "Design" below. Read it before starting.

## Design (agreed)

- The visitor sees `Order API → Queue → Workers → Payment / Inventory / Email`, with a Dead-letter box, a metrics panel and an event log.
- Chaos buttons and the recovery each one demonstrates:
  - **Kill a worker:** the unacked message is redelivered.
  - **Send a duplicate:** the idempotency key blocks the second copy.
  - **Slow the database:** timeouts, then retries with exponential backoff.
  - **Poison message:** dead-lettered after `MAX_ATTEMPTS`, while other orders keep flowing.
  - **Traffic spike:** the queue absorbs the burst and workers scale up, then back down.
- "Write the incident report" sends only the structured event log, never free text from the visitor. The report is labelled "Generated by Claude from this session's logs". If the API fails or the cap is reached, the page shows a built-in sample report, labelled as a sample.
- Phase 5 (a real RabbitMQ + Python/Java version in a separate repo) is **out of scope** for this plan.

## Review Focus

1. **Tab hidden, then resumed:** `requestAnimationFrame` resumes with a huge `dt`. The engine must clamp each tick to `MAX_TICK_MS` and not burst-process minutes of simulated time. Pinned in Task 1 (`tick clamps large dt`).
2. **Button spam:** pressing "Traffic spike" or "Kill a worker" many times must not grow memory without limit or leave workers dead forever. The queue caps at `QUEUE_CAP` (extra orders count as `rejected`), and every killed worker restarts. Pinned in Task 2 (`queue cap rejects overflow`, `kill spam recovers`).
3. **Long sessions:** the event list stays at most `MAX_EVENTS`, and the incident log stays under the Lambda's 16 KB limit however long someone plays. Pinned in Task 1 (`events are capped`) and Task 3 (`log stays under 16KB`).
4. **Hostile or garbage POST to the Lambda:** non-JSON input, extra fields, free-text strings, oversized bodies or unknown event types are rejected with 400 before Claude is called. That way the endpoint can't be used as a free Claude proxy or for prompt injection. Pinned in Task 4.
5. **Report request fails or is slow:** a double-click must not send two requests, and a network error or a 429 must show the sample report rather than an error. Pinned in Task 7.

- Produces (used by every later task):

```ts
export type ChaosAction = 'killWorker' | 'duplicate' | 'slowDb' | 'poison' | 'spike';
export type EventType =
  | 'received' | 'started' | 'processed' | 'timeout' | 'failed' | 'retry_scheduled'
  | 'dead_lettered' | 'duplicate_blocked' | 'worker_killed' | 'worker_restarted'
  | 'redelivered' | 'scaled_up' | 'scaled_down' | 'rejected' | 'chaos';
export interface SimEvent { t: number; type: EventType; orderId?: string; workerId?: number; attempt?: number; chaos?: ChaosAction }
export interface Message { orderId: string; attempts: number; poison: boolean; availableAt: number; enqueuedAt: number }
export interface Worker { id: number; alive: boolean; current?: Message; startedAt?: number; doneAt?: number; restartAt?: number }
export interface Metrics { processed: number; retries: number; timeouts: number; duplicatesBlocked: number; deadLettered: number; redelivered: number; rejected: number; queueDepth: number; aliveWorkers: number; avgLatencyMs: number }
export interface Snapshot { now: number; queue: Message[]; workers: Worker[]; deadLetter: Message[]; metrics: Metrics; slowDbUntil: number }
export const CONFIG: {
  ARRIVAL_MS: 700; PROCESS_MS: 400; SLOW_PROCESS_MS: 2500; TIMEOUT_MS: 1500;
  SLOW_DB_DURATION_MS: 6000; MAX_ATTEMPTS: 4; BACKOFF_BASE_MS: 500;
  BASE_WORKERS: 3; MAX_WORKERS: 6; SCALE_UP_DEPTH: 10; WORKER_RESTART_MS: 3000;
  SPIKE_ORDERS: 30; QUEUE_CAP: 200; MAX_TICK_MS: 250; MAX_EVENTS: 500;
};
export class OrderSystem {
  constructor(opts?: { autoArrivals?: boolean }); // default true
  tick(dtMs: number): void;          // clamps dtMs to CONFIG.MAX_TICK_MS
  enqueueOrder(orderId?: string, poison?: boolean): void; // default id `o-<n>`
  apply(action: ChaosAction): void;  // implemented in Task 2; Task 1 records only the 'chaos' event
  snapshot(): Snapshot;              // returns copies, never live references
  events(): SimEvent[];
}
```

Core semantics for Task 1:
- **Arrivals:** with `autoArrivals`, every `ARRIVAL_MS` the engine enqueues `o-<n>` and emits `received`.
- **Picking up work:** an idle, alive worker takes the first message with `availableAt <= now` and emits `started`. Processing takes `PROCESS_MS`, or `SLOW_PROCESS_MS` while `now < slowDbUntil`.
  - If the processing time is greater than `TIMEOUT_MS`, the attempt ends at `TIMEOUT_MS` with `timeout`.
  - A poison message ends with `failed`.
  - Otherwise the attempt ends with `processed`, which adds the id to the processed set and updates `avgLatencyMs` from `enqueuedAt`.
- **Failed attempts:** a timeout or failure increments `attempts`.
  - If `attempts >= MAX_ATTEMPTS`, the message moves to `deadLetter` with `dead_lettered`.
  - Otherwise it's requeued with `availableAt = now + BACKOFF_BASE_MS * 2^(attempts-1)`, emitting `retry_scheduled` and incrementing `retries`.
- **Idempotency:** before starting work, a worker checks the processed set. If the order id is already in it, the message is acked with `duplicate_blocked` and no work is done.
- **Event cap:** the event list drops its oldest entries beyond `MAX_EVENTS`.

### Task 2: Chaos actions

**Files:**
- Modify: `src/redesign/chaos/engine.ts` (`apply`, scaling inside `tick`)
- Test: `src/redesign/chaos/engine.test.ts`

**Interfaces:**
- Consumes: `OrderSystem`, `CONFIG` from Task 1.
- Produces: `apply(action)` with the behaviour below. Every call also emits `{type:'chaos', chaos: action}`.

Semantics:
- **`killWorker`:** kills the first alive busy worker, or the first alive worker if none are busy, and emits `worker_killed`. Its `current` message goes back to the head of the queue with its `attempts` unchanged, emitting `redelivered` and incrementing `redelivered`. The worker gets `restartAt = now + WORKER_RESTART_MS`, and `tick` revives it with `worker_restarted`. If no worker is alive, nothing happens.
- **`duplicate`:** re-enqueues the most recently processed order id. If nothing has been processed yet, it enqueues one new order twice.
- **`slowDb`:** sets `slowDbUntil = now + SLOW_DB_DURATION_MS`.
- **`poison`:** enqueues `p-<n>` with `poison: true`.
- **`spike`:** enqueues `SPIKE_ORDERS` orders. When the queue length reaches `QUEUE_CAP`, extra orders are dropped with `rejected`, incrementing `rejected`.
- **Scaling** (in `tick`, at most one action per tick):
  - If `queueDepth > SCALE_UP_DEPTH` and there are fewer than `MAX_WORKERS` workers, add one worker with `scaled_up`.
  - If `queueDepth === 0` and there are more than `BASE_WORKERS` workers, remove one idle worker with `scaled_down`.

### Task 4: Lambda validation and handler

**Files:**

**Interfaces:**
- Consumes: the `IncidentLog` JSON shape from Task 3.
- Produces:
  - `validateIncidentLog(raw: string): { ok: true, log } | { ok: false, error: string }` in `validate.mjs`
  - `checkLimits(ip: string): Promise<'ok' | 'ip' | 'daily'>` in `limits.mjs`
  - `writeReport(log): Promise<string>` in `report.mjs`
  - `handler(event)` in `index.mjs`, which returns `{ statusCode, headers, body }`. A success body is `{"report": "<text>"}`, and an error body is `{"error": "..."}`.

Validation rules:
- The raw body must be ≤ 16384 bytes and parse as JSON.
- The top-level keys must be exactly `durationMs, metrics, chaos, counts, events`.
- Every number must be finite and ≥ 0.
- `metrics` must have exactly the `Metrics` keys, all numbers.
- `chaos[].action` and `events[].chaos` must be valid `ChaosAction` values.
- `events.length` must be ≤ 300. Each event's keys must be a subset of `t, type, orderId, workerId, attempt, chaos`, and `type` must be a valid `EventType`.
- `orderId` must match `/^[op]-\d{1,6}$/`.
- `counts` keys must be valid `EventType` values.
- No other strings are allowed anywhere.

Limits (`limits.mjs`, table name from env `TABLE_NAME`, uses `UpdateItem` with `ADD #c :one` and a condition):
- **Per IP:** key `ip#<ip>#<YYYY-MM-DDTHH>`, condition `attribute_not_exists(#c) OR #c < :ipCap` with `:ipCap = 5`, `ttl` = now + 2h.
- **Daily:** key `day#<YYYY-MM-DD>`, condition `#c < :dayCap` with `:dayCap = 200`, `ttl` = now + 2d.
- A `ConditionalCheckFailedException` maps to `'ip'` or `'daily'`.

Report (`report.mjs`):

```js
const client = new Anthropic(); // reads ANTHROPIC_API_KEY

  model: 'claude-opus-5-5', max_tokens: 8000,
```

Behaviour:
- **`useSimulation`:** keeps one `OrderSystem` in a ref. A `requestAnimationFrame` loop calls `sim.tick(dt)`, and the hook publishes `snapshot()` to state at most every 100 ms. The loop pauses while `document.hidden` and is cleaned up on unmount. `reset()` creates a new `OrderSystem`.
- **`Diagram`:**
  - Columns: Order API → Queue → Workers → Payment / Inventory / Email.
